# 版本演进：从 v1 到 v3

Spatial Agent Runtime 并非一次性完成的纸面设计。它经历了多轮 ArcGIS Pro 现场运行、对抗性测试与架构审查，每个版本都回答了一个不同的问题。

## v1——LLM 能否操作 GIS

第一个版本是纵向集成的 ArcGIS Pro 插件。它将自然语言请求连接到 GP 执行，并引入 `/run` 命令、项目上下文、RAG 知识、Skills 与后置条件检查。

v1 证明了：

- 自然语言 GIS 工作流可以在桌面宿主内执行；
- 领域上下文与工具文档能够显著改善规划质量；
- 仅有结果消息并不足够，还必须检查真实地图与数据集状态；
- 用户需要可见进度、记忆能力与自修复路径。

v1 同时暴露了：

- UI、模型、执行与验证之间耦合过紧；
- 文本命令解析无法形成持久、稳定的工具协议；
- 安全决策分散，难以独立测试；
- “工具执行成功”经常被误认为“用户目标已完成”。

## v2——能否演进为 Runtime

v2 采用绞杀者模式逐步重写。首先建立稳定的 Contracts，随后引入与宿主无关的 Runtime 与显式 Adapters。原生工具调用替代了最初的纯文本控制链路，项目由单一插件演进为分层 Runtime。

v2 的主要进展：

- 建立 Contracts / Core / Runtime / Adapter 分层边界；
- 引入有界 ReAct 循环与结构化 Observation；
- 通过三重名称身份管理大规模 manifest 驱动的 GP 工具，并完成过 2,001 个接口的本地验证；
- 建立四级安全分类与基于数据影响范围的审批；
- 将破坏性操作备份设为硬性约束；
- 引入 Transcript、Verification Ledger、Snapshot 与 Audit Log；
- 建立 Checkpoint、项目记忆与上下文预算；
- 提供本地知识检索、Skills 与只读 MCP 能力面；
- 通过架构测试强制约束依赖方向。

v2 最关键的经验是：控制流安全并不等于结果正确。即使调度器本身安全，仍可能操作错误目标、重复已完成工作，或者在原始意图尚未满足时报告成功。

## v3——完成结果能否被信任

v3 将语义目标移出模型生成的计划。Planner 只能在独立 Goal Contract 的约束下提出物理工作；目标覆盖、能力、参数与证明义务会在执行前后分别评估。

v3 的主要进展：

- 语义化 Goal Contract 与明确的轮次关系；
- 跨显示名称、数据集和血缘关系的稳定资源身份；
- 目标覆盖以及能力/证明闭包；
- 渐进式可采纳性：安全探查与有效目标子集可以推进进度，但不能制造虚假完成；
- 调用影响规划与资源感知的宿主修订检查；
- 稳定 Action ID 与精确批次审批；
- 持久 GIS 事务顺序：预检、备份、重建基线、执行、验证；
- 针对量算方法、单位与精度的参数级数值证明；
- 高于模型叙述优先级的确定性完成报告；
- Session Lease 与下次启动时的过期会话恢复；
- 面向语义空响应的有界恢复机制。

## 工程经验

1. **证据必须强于叙述。** 模型文本可以解释结果，但不能定义结果。
2. **意图与计划是不同对象。** 否则 Planner 可能将目标意外缩小为它已经完成的部分。
3. **安全取决于最终参数。** 仅凭工具名无法判断操作范围、覆盖行为或可逆性。
4. **宿主状态是一种并发状态。** 用户与 Agent 都可能修改 ArcGIS Pro，因此审批与计划必须绑定状态修订版本。
5. **失败也是产品需求。** 空响应、宿主退出和部分执行都需要一等的终态语义。
6. **现场测试能够发现架构缺陷。** 多项关键契约都源自这样的真实运行：单个工具执行正常，但整体工作流仍然失败。

当前 v3 已将概率性规划限制在确定性合同、安全策略与证据闭环之内。后续演进将继续围绕宿主验证、工具治理、模型适配与性能测量展开。

公开发行阶段进一步将厂商生成的工具目录、帮助内容与风险快照移出 Git 历史，改为由使用者在已获许可的环境中本地生成。该变更不改变 Runtime 的架构结论，但让原创代码的 MIT 授权边界与第三方软件许可边界保持分离。
